## 1. 目录约定



```
game-lab/
├─ engines/     引擎与工具（体积大，不入版本控制，仅保留 README）
├─ projects/    每个游戏形态一个独立子目录
├─ assets/      跨项目复用的美术 / 音频 / 字体
├─ tools/       自建脚本（环境探测、构建、验证）
├─ docs/        技术选型笔记与踩坑记录
└─ README.md
```

本 lab 遵循 `F:\Dev\Projects\<name>-lab\` 的既有约定（agent-lab /ros2-lab /ml-lab/matlab-lab）。

系统级工具（dotnet、Java、MATLAB）继续留在 `F:\Dev\Tools\`；引擎按需下载到本 lab 的 `engines/`。

**projects/ 命名约定**：`NN-形态简称`，编号连续，一眼看出先后顺序。

例如 1-voxel-field-prototype、3-web-3d-racer。

| **Blender**  | 完全可以             | 官网下载 Windows zip（Portable），解压即用                                    | GPL，免费                      | 约 300–500 MB                      |
| **Unity 6**  | 部分可以             | 必须先装 **Unity Hub**（安装程序，落系统盘）；编辑器安装路径可在 Hub 设置中改到 `engines/unity/` | Personal 免费，但**需登录账号激活许可证** | Hub 约 200 MB + 编辑器 5–15 GB（随模块增减） |
| **Unreal 5** | 不建议              | 通过 Epic Games Launcher 安装；源码版需关联 Epic 账号后从 GitHub 拉取并自行编译          | 免费但需账号                      | 含源码可达 100 GB+                     |

> 体积为
>
> **量级估计，未实测**
>
> 。实际下载前会先报具体数字再执行。

**结论**：Godot 与 Blender 可以完全按你的要求落在 `engines/` 内，随删随装、零系统残留；Unity 只能做到「编辑器落在 engines/，Hub 落系统」，并且需要你手动完成一次账号登录激活 —— 这一步我无法代劳。

## 3. 自动化验证能力矩阵

这是本实验室最需要先明确的事：**「能写代码」不等于「能验证结果」**。下表决定了我对每类项目的实际交付确定性。



| 引擎 / 技术栈                    | 无头模式                                 | 我能自动完成                          | 我无法完成             |
| --------------------------- | ------------------------------------ | ------------------------------- | ----------------- |
| **Godot 4**                 | `godot --headless`                   | 资源导入、脚本报错检查、GUT 单元测试、导出构建       | 看画面、调手感、UI 布局     |
| **Blender**                 | `blender --background --python s.py` | 程序化建模、批量导出 glTF/GLB、渲染静帧        | 手工雕刻、风格与审美判断      |
| **Unity 6**                 | `-batchmode -nographics -quit`       | 编译检查、EditMode/PlayMode 测试、命令行构建 | 需先激活许可证；编辑器内画面与手感 |
| **网页端**（three.js/ Rapier 等） | 无头 Chrome + CDP                      | **完整**：真实点击、读回游戏状态、截图核对、捕获运行时报错 | —                 |

**读法**：越往下，交付的确定性越高。网页端是唯一能做到「跑通才算完成」的一档。当前所有项目都在网页端。

## 4. 快速开始



```
node tools/check-env.mjs     # 引擎与工具链就位状态（含实测版本号）
node tools/probe-gpu.mjs     # 浏览器侧渲染能力探测（需先启动 Chrome 调试实例）
```

输出引擎就位状态与下一步建议。

### 无头浏览器验证环境

网页端项目的自动验证依赖一个开着调试端口的 Chrome。启动方式：



```
chrome.exe --headless=new --remote-debugging-port=9222 \
  --user-data-dir="F:/Dev/Projects/game-lab/_tmp/chrome-profile" \
  --no-first-run --no-default-browser-check about:blank
```

**不要加&#x20;**`--disable-gpu`，否则拿不到任何 GPU 信息。

**⚠️ 性能数据的可信度取决于渲染器，而它并不稳定**

实测记录（同一台机器、同一 Chrome 版本 `153.0.8010.52`、同一启动参数）：



| 日期    | 渲染器                                 | 基线帧率          |
| ----- | ----------------------------------- | ------------- |
| 09-21 | Microsoft Basic Render Driver（软件回退） | 40.7 fps      |
| 09-22 | NVIDIA GeForce RTX 4060（真实 GPU）     | **165.1 fps** |

**同一项目、同一环境，结论差 4 倍。** 因此：



* **每次验证都要实测渲染器，不要假设**（探测工具：`tools/probe-gpu.mjs`）

* 软件渲染下：帧率只可用于**相对比较**，必须显式标注

* 真实 GPU 下：绝对帧率可信；但若恰等于刷新率（165fps），说明撞到 rAF 上限，真实余量未知

* `navigator.gpu` 在无头环境**始终不存在**，WebGPU 路径无法自动验证

## 5. 版本固定

引擎版本一经选定即写入 `docs/versions.md`，不在项目间混用。

理由：Godot 4 的小版本之间存在过资源格式与 API 的破坏性变更；Unity 工程跨版本升级会触发长时间重新导入。

## 6. 已知风险



1. **Windows 长路径限制**（260 字符）。引擎工程的 `Library/`、`.godot/` 缓存路径较深，本 lab 路径刻意保持短，`projects/` 下不要再多层嵌套。

2. **Godot .NET 版与 .NET SDK 版本**：本机 `dotnet` 为 10.0，而 Godot 4.x 的 C# 目标框架通常为 `net8.0`。能否直接复用需实测，必要时单独安装匹配版本的 SDK。

3. **Unity 首次启动**：登录、激活、下载模块全程需人工介入，且耗时可能较长。

4. **engines/ 不入版本控制**：已写入 `.gitignore`。项目内引用引擎一律用相对路径或环境变量，不要写死绝对路径。
