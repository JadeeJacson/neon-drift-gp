## 1. P0-1 · 战败伤害记账错误（输了一场不掉血）

### 现象

`tools/sim_report.gd` 的单局明细里反复出现「**负 掉血0**」：

```
S9    18s 负 掉血0 (HP94 )  我方 6 个/战力956 vs 敌方 6 个/战力1217
S10   20s 负 掉血0 (HP94 )
S11   13s 负 掉血12(HP82 )
S12B  34s 负 掉血0 (HP82 )
```

打了 18 秒输了，玩家一点血不掉。难度曲线在这里是**断开**的。

### 根因

`sim/run_state.gd:373`：

```gdscript
func _survived(sim: BattleSim, enemy_def: Dictionary) -> bool:
	for u in sim.units:
		if bool(d["is_ally"]):
			continue
		if String(d["id"]) == String(enemy_def["id"]) and d["cell"] == enemy_def["cell"]:
			return bool(d["alive"])
	return false
```

`enemy_def["cell"]` 是**编成时的初始格子**，而 `d["cell"]` 是**战斗结束时的格子**。
自走棋的敌人一定会移动（射程外就朝目标走），一移动两者就对不上 → 返回 false → 不计伤害。

### 实测判据

临时诊断脚本跑 12 seed × 全阶段，仅统计败场：

```
败场 36 场，其中伤害记账与真实存活不符 21 场 (58%)
败场中「明明有敌人存活却记账 0 伤害」 14 场 (39%)
```

### 修法

伤害不该逐个匹配 `enemy_def`，直接按 `side` 统计 sim 结束时的存活者：

```gdscript
for u in sim.units:
    if int(u["side"]) == Board.ENEMY and bool(u["alive"]) and not bool(u["is_summon"]):
        dmg += 2 * int(u["star"]) + 1
```

召唤物是否计入需要决策（建议**排除**：掉血只应由「编成」决定，才对得上 StageTable 的预算曲线）。
`_enemy_survives`（`run_state.gd:419`）是同一逻辑的死代码副本，一并删除。

### 修复后的影响（已实测，20 seed）

| 画像 | 当前通关率 | 修复后 | 当前均掉血 | 修复后 |
|---|---|---|---|---|
| 龟缩流 | 0% | 0% | 112.5 | 118.5 |
| 普通 | 75% | **75%** | 26.6 | **49.8** |
| 高手 | 65% | **65%** | 31.4 | **46.0** |

**通关率不变，但均掉血接近翻倍。** 原因是失败条件是「HP ≤ 0」而 HP 上限 100，
平均掉 49.8 还死不了；只有极端连败才出局。所以：

- 难度曲线**不需要推倒重来**，要重标定的是**生命缓冲与评级阈值**
  （`Hud.grade()` 看 `hp_left`，现在 S 级门槛 `hp ≥ 70` 会变得几乎拿不到）。
- `test_match_sim.gd` 的基线要重测一遍再确认区间（目前没有 damage 硬断言，所以不会直接失败）。

## 2. P0-2 · 星辉羁绊是死羁绊，永远激活不了

### 根因

`sim/traits.gd:97` 的兜底分支（kind = `"star"`）：

```gdscript
static func _matches(def: Dictionary, unit: Dictionary) -> bool:
	...
	return int(unit["star"]) >= int(def["tiers"][0]["need"])
```

它判定的是「**这个单位的星级 ≥ 6**」，而 `UnitTable.MAX_STAR = 3`。
所以这个条件恒为 false——**5 条羁绊实际只有 4 条**。

### 实测判据

```
星辉 need=6，_matches(1★单位)=false  _matches(3★单位)=false
6 个 1★ 同星：激活 2 条 -> 圣团 III, 近卫 II   （没有星辉）
```

### 修法

语义应该是「**同一星级的单位是否达到 6 个**」，即按星级分组计数取最大值：

```gdscript
if kind == "star":
    var by_star := {}
    for u in units:
        by_star[int(u["star"])] = int(by_star.get(int(u["star"]), 0)) + 1
    var best := 0
    for k in by_star:
        best = maxi(best, int(by_star[k]))
    return best >= int(def["tiers"][0]["need"])
```

附带修文案：`traits.gd:54` 的 desc 写「5 个 / +12%」，实际是 6 个 / +10%，玩家在 HUD 上看到的是错的。

## 3. P0-3 · 召唤物阵营标记错误

`sim/battle_sim.gd:411`：

```gdscript
var nu := _make_unit("sk_minion", 1, my_side, cell, true, {})
```

第 5 个参数 `is_ally` **硬编码 true**。敌方术士召唤出的仆从因此被标记为我方。
`_make_unit` 里 `is_ally` 同时承担两件事——「查哪张数值表」和「属于哪一阵营」——这是设计缺陷。

**已被影响的地方**：

- `run_state._survived()`：用 `is_ally` 过滤，敌方召唤物被跳过。
- `battle_director.setup():73`：`view.setup(..., bool(u["is_ally"]))` → 敌方召唤物会显示**绿色血条**（我方色）。
- `unit_view._tint()`：同上，敌方召唤物不做敌方 tint。

文档 §9.0 记录了「用 `side` 记账」的修法，但那是在 `battle_director` 里绕过的，**根因没修**。

**修法**：把「查表来源」与「阵营」拆成两个参数，`is_ally := (side == Board.ALLY)`。

## 4. P1-1 · 手动摆位完全没接上（自走棋最大的决策维度是关着的）

`RunState` 里 `place_unit()` / `move_board_unit()` 写好了，`BoardView` 里 `set_hover()` /
`set_selected_bench()` / `move_unit()` / `world_to_cell()` 也写好了。grep 全部调用点后确认：

- `place_unit` / `move_board_unit`：**只在 `test_economy.gd` 里被调用**，生产代码零调用。
- `set_hover` / `set_selected_bench` / `move_unit`：**定义后无人调用**，纯死代码。

玩家侧唯一的布阵入口是 `A`（自动上阵）→ `Board.auto_place_cell()`。也就是说
**「坦克放前排、法师缩后排」这个自走棋的核心决策，玩家根本做不了。**

这正好接上文档 §3.2 的已知缺口：「普通与高手打平，需要新机制而不是调参」。
**机制的接口已经写好了，缺的只是输入与交互层**——鼠标拾取格子 → 选中备战位 → 落子。

### 与「自动布阵全是前排」叠加后更糟

实测 6 个单位全部落在 **row 4**（最靠近敌方的一行）：

```
6 个单位落在：{ 4: 6 }
```

因为 `auto_place_cell` 从 `rows_for(ALLY)[0]`（= 4）开始填，8 列没填满就不会用 row 5，
而人口上限正好是 6。后果：

- 我方永远一字排开贴脸，**远程没有任何保护**；
- 「齐射」（3 个 back）这类后排羁绊在观感上完全不成立；
- 战斗画面是 6 个人挤一排，不好看也不好读。

**建议**：`auto_place_cell` 按 role 分层（front → row 4-5，back → row 6-7），
再补手动摆位。两件事一起做，站位才真正成为决策。

## 5. P1-2 · 暗影领主从未出场

`stage_table.gd:80`：

```gdscript
var boss_id := "b_sking" if stage != 8 else "b_lord"
```

而 `BOSS_STAGES := [6, 12, 18]`——`stage` 永远不会等于 8，所以 **`b_lord` 是死分支**。
实测三个 Boss 阶段全是骷髅王：

```
阶段 6 -> 骷髅王    阶段 12 -> 骷髅王    阶段 18 -> 骷髅王
```

`EnemyTable` 里定义好的「暗影领主」（1750 HP / range 3 / 远程法师 Boss）和
`UnitView.ENEMY_APPEARANCE` 里的 `b_lord: "mage"` 都白写了。3 场 Boss 战打同一个 Boss，
后期缺少变化。

**修法**：按阶段索引取 Boss，例如 `BOSS_STAGES.find(stage)` 映射到 `[b_sking, b_lord, b_sking]`，
或给 `BOSS_STAGES` 配一张 boss id 表。

## 6. P2 · 工程与测试质量

### 6.1 整个 09 工程没有被 git 跟踪

```
git ls-files projects/09-arcane-roster | wc -l  →  0
find projects/09-arcane-roster -type f | wc -l  →  1172
```

与 11 号当初同款风险：**误删无法恢复**。08 也是 0 入库。建议优先做一次全量入库。

### 6.2 断言过弱，导致 P0 bug 一路绿灯

| 位置 | 现在断言 | 问题 |
|---|---|---|
| `smoke_battle.gd:120` | `run.hp <= hp_before`「掉血记账生效」 | 只验「没加血」，**掉 0 血照样通过** |
| `test_match_sim.gd:122` | `if not win: assert_gt(dmg, 0)` | 包在 `if` 里，且**只测一场**；那场恰好没触发 |

**改法**：把「败仗伤害 == sim 中 side=ENEMY 的存活者星级和」写成**无条件对账断言**，
并遍历多 seed，不靠单场运气。这一条是防止 P0-1 复发的关键。

### 6.3 `income()` 无条件发放「提前开战奖励」

`run_state.gd:76`：`var early := float(EARLY_START_BONUS)` 无条件计入收入。
而 `game_root._on_ready()` 按 F 时又 `run.gold += 1`。结果：

- 按 F 提前开战 → 拿 2 次（当场 +1，下阶段 +1）；
- 等满 35 秒 → 也白拿 1 次，「提前开战」失去意义。

### 6.4 文档与代码不一致（小）

- §2.5 写预算基数 `240`，代码是 `BUDGET_BASE := 270.0`（§3 的表格 390 与代码一致，是 §2.5 写错）。
- 星辉 desc「5 个 / +12%」vs 代码「6 个 / +10%」。

### 6.5 1 个 risky 测试

`test_place_unit_rejects_illegal` 报 `[Risky]: Did not assert`。它调用了
`place_unit` 但断言写在 `assert_false` 之外，实际没断言——顺带说明这个「摆位」接口确实没人用。

## 7. P3 · 表现层（需制作人实跑才能定）

文档 §9.1 列的 8 项人验**全部未做**，制作人还没实跑过。除此之外代码层面还有两处待观察：

1. `battle_director._sync_views()` 每 tick 为单位移动 `create_tween()`，未 kill 前一个 tween，
   单位连续移动时可能堆积。
2. `game_root._rebuild_units()` 每次买/卖/合成都 `clear_units()` + 全量重建视图
   （实例化 GLB + 血条 + 星级），备战阶段高频操作会有可感知开销。

单场战斗时长方面，明细里出现 S12B **34 秒**（目标 10–18 秒），`test_match_sim` 的上界是
26 秒中位数，暂时安全，但超时场次值得单独用 `tools/probe_battle.gd` 查一下是不是坦克对耗。
