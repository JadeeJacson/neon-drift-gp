# 00 · 3D 游戏实验室路线图

> **这份文档是 lab 的选题入口与质量基线。** 开新项目前先查这里：这个形态属于哪一格？当前短板是什么？
>
> **定位（2026-09-24 重定）**：只做 **3D 网页游戏**，要求**能完整玩一遍、效果能看**。
> 不做技术 Demo，不做半成品。每个项目交付时都应是一个从打开到通关/跑完一局能自洽结束的完整游戏。
>
> **质量标尺**：参考 [riba2534/claude-opus-5-5-demo](https://github.com/riba2534/claude-opus-5-5-demo) 那一档——
> 单文件/少量模块、程序化资产、完整玩法循环（操作 → 反馈 → 结束）、无肉眼可见的画面错误。

---

## 0. 硬约束

1. **真 3D**：透视相机 + 3D 空间，不做 2D / 2.5D 正交视角。
2. **完整玩法循环**：有开始、有进行中状态、有结束条件（通关/胜负/时间到/得分结算）。
   「会走会跳会点 3 个东西」不算完整游戏。
3. **零外部美术/音频资产**：全部程序化生成（canvas 画贴图、shader 做效果、WebAudio 合成音效）。
4. **能看**：不允许纯色大盒子 + 平行光这种占位渲染。至少要有：基础光照、氛围（天空/雾/后处理之一）、
   操作反馈（粒子/音效/屏幕震动/HUD 之一）。
5. **无头可验证**：加载无报错、核心流程可被 CDP 脚本跑通。画面手感仍需人眼验收。

## 4. 交付定义（DoD）

项目「完成」= 同时满足：

1. `npm run typecheck` **0 错误**。
2. 无头 CDP 验证脚本全绿：加载无报错、核心玩法可脚本跑通、无 console error。
3. 人眼验收：从打开到通关/跑完一局，视觉和手感不刺眼、不穿模、无明显画面错误。

## 5. 已沉淀的技术教训

> 这些是之前项目踩过的坑，不随项目删除作废。

### 5.1 无头验证

- **耗时类指标（FPS / `renderMs`）在 headless 下不可信**：FPS 被 rAF 节流，`renderMs` 是亚毫秒噪声（0ms/1ms 会反转）。
  规模结论只看三角面数 / draw call / 可见块数。
- 读 `renderer.info.render.*` 前必须强制 `scene.render()` 一帧，否则读到上一帧陈旧值。
- 性能数据可信度取决于渲染器：同一台机器同一 Chrome 版本，软件回退和真 GPU 的帧率差 4 倍。
  每次验证都要实测渲染器（`tools/probe-gpu.mjs`），不要假设。
- Rapier 无头确定性已实测：同输入末态完全一致，可用于机器人自动跑关卡。

### 5.2 渲染优化（来自已删的体素沙盒，结论保留）

- **面剔除**是最高性价比优化：默认场景三角面 -52.8%，8×8 场景 -65.2%。
- **贪心网格合并**再降到 1.4% 三角面，但合并后丢失 per-instance 身份，**编辑态不能用**。
- 视锥剔除有效（64 块中 55 块参与渲染）。

### 5.3 可玩性底线

- **工程化分层、自动化验证、性能优化指标都不能替代可玩性。**
  验证脚本只告诉你「有没有崩」，不告诉你「好不好玩」。
- 一个 3D 游戏要能玩，至少要有：物理/碰撞（不穿模）、操作反馈（粒子/音效）、
  明确的胜负条件。缺任何一个都是技术 Demo，不是游戏。

### 5.4 把「手感」转成可测数字

03 的方法论：把加速、极速、过弯速度损失、圈速量化成指标，用机器人跑分做参数扫描。
这让「调校敏感」进入自动验证范围——不替代人工试驾，但把搜索空间缩到可裁决量级。
