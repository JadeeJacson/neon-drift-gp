## 2. 核心机制（最终实现）

### 2.1 一局循环

```
开局（10 金 + 3 人口）→ 阶段 1..18 循环：
  备战 PLANNING（35s 倒计时，提前开战 +1 金）
     ├─ 1-5 买商店位 · R 刷新（2 金）· C 合成 · A 自动上阵 · X 卖备战单位
     └─ 羁绊按人数门槛自动判定并显示
  战斗 BATTLE（BattleDirector 逐 tick 驱动 sim，1/2/4 倍速）
  结算 SETTLE：胜 → +连胜与赏金；负 → 掉血 = 敌方存活单位星级和（BOSS 战 ×1.5）
终局：生命 ≤ 0 → 失败；打赢第 18 阶段 BOSS → 通关（评级 S/A/B/C）
```

### 2.2 棋盘与战斗规则

| 项 | 实现值 |
|---|---|
| 棋盘 | 8 列 × 8 行。我方 5–8 行，敌方 1–4 行，行 0 在远端（敌方后排） |
| 格子边长 | 2.2 m（> 角色宽 1.94 m，相邻单位不穿插） |
| 距离 | **切比雪夫**（斜向相邻也算打得到）。用曼哈顿会出现「差一格却打不到」 |
| 移动 | 定长 tick（0.25s）一步一格，候选顺序固定且**所有候选都不增距离** |
| 索敌 | 射程内按策略（近战最近 / 远程点最深 / 补刀残血）；**射程外也要锁定最近敌人并走过去** |
| 嘲讽 | 唯一硬控制，压过所有策略 |
| 伤害 | `max(1, atk×暴击 − 护甲)`，下限 1 是硬约束（否则高护甲被无限防） |
| 技能 | 8 种 kind：嘲讽 / 范围 / 暴击 buff / 突进 / 中毒 AoE / 召唤 / 护甲 buff / 死亡爆碎 |
| 人口 | 3 起，随阶段 +1（每 2 阶段），赢一场 +1，上限 6 |
| 星级 | 1★/2★/3★，3 合 1；模型放大 12%/26%，血量 ×2.3/×5.0，攻击 ×1.95/×3.6 |

### 2.3 经济（`sim/run_state.gd`，全部可测）

| 收入项 | 公式 | 设计意图 |
|---|---|---|
| 回合基础 | `5 + floor(stage/2)` | 后期不依赖连胜 |
| 利息 | `min(floor(金币/10), 5)` | 攒钱是有效策略 |
| 连胜赏金 | `min(1+连胜, 6)` | 高风险高回报 |
| 连败补偿 | 连败 ≥2 起每场 +1，上限 3 | 防「输了就死循环」劝退 |
| 出售返还 | 1★=1 / 2★=3 / 3★=9 | 换阵容不吃亏（2★ 售价覆盖三个 1★ 的成本） |
| 提前开战 | +1 | 奖励果断 |

### 2.4 阵容与羁绊

9 个 KayKit 角色 × 3 星级 = 27 个条目；**阵容深度靠 5 条羁绊**：

| 羁绊 | 门槛 | 效果 |
|---|---|---|
| 圣团（Adventurers） | 2/4/6 | 全体 +10% / +25%攻+25%血 / +50%攻+50%血 |
| 亡者军团（Skeletons） | 2/4 | +20%攻 / +40%攻+3%闪避 |
| 近卫（role=front） | 3/5 | 护甲 +3 / +6 |
| 齐射（role=back） | 3 | 攻速 +15% |
| 星辉（同星级） | 6 | 全体攻击 +10% |

### 2.5 敌方编成（难度唯一入口，`sim/stage_table.gd`）

```
预算(stage) = 270 + 前6阶段每阶段120 + 之后每阶段88 + max(连胜,0)×25
人数(stage) = clamp(3 + (stage-1)/2, 3, 6)；Boss 阶段 +1 随从位
精英率      = min(0.78, 0.30+0.10×(stage-5))，第 8 阶段起 3★ 率 min(0.42, …)
```

实测（`tools/preview_rounds.gd`，6 组编成取平均）：

| 阶段 | 预算 | 人数 | 敌方战力 | 精英率 |
|---|---|---|---|---|
| 1 | 390 | 3.0 | 224 | 0% |
| 5 | 870 | 5.0 | 522 | 47% |
| 9 | 1254 | 6.0 | 979 | 78% |
| 18 ★ | 2046 | 6.0 | 1236 | 75% |

**「6 个 1★ 不做任何运营」打全程的胜率 = 36%**，单场平均 12.5 秒（目标 10–18 秒）。
这是本作的难度标尺：真玩家（会升星会成型）应明显高于它，而龟缩流（3 个便宜货）低于它。

### 3.2 已知缺口（2026-09-28 已解决，留档）

**「普通与高手打平（65% vs 65%）」——已由摆位维度打破，高手 60% > 普通 55%。**

当时试过四种「更聪明的打法」，全部实测更差：

1. **囤利息是陷阱**：收入是平的（每回合 10–15 块），攒钱没有复利，钱放着 = 少一个人口 = 输。「留 20 块」的高手 70% < 「留 10 块」的普通 80%。
2. **每回合刷商店是负收益**：单阶段 8 块刷新钱够买两个单位了（42% 通关）。
3. **「冲主 C 只买一个单位」也不成立**：牺牲了羁绊与宽度，实测 25%–67% 波动，最差。
4. **只买便宜**：直接退化成龟缩流。

**真正的答案是第 5 种**：当时以为「再加决策维度需要新的机制（装备/转职/羁绊传导）」，
实际上**手动摆位这个核心决策维度压根没接上**（`place_unit`/`move_board_unit` 全是死代码，
玩家只能 A 键自动上阵，且自动布阵把所有人堆在最前排一排）。接上摆位 +
布阵按职能分层 + 战斗允许越中线追击之后，高手画像立刻反超。
断言保持「高手 ≥ 普通 − 25%」以容忍噪声，但意图已升级为「高手 > 普通」。

### 4.1 实测得出的三个实现约束（不实测就会踩）

1. **KayKit 里没有 Walk/Run 动画**，真实名字是 `Walking_A` / `Running_A`。
2. **Knight 的 GLB 里 5 个武器节点全部带网格**（`1H_Sword`/`2H_Sword`/三面盾），
   直接实例化会同时挂 5 把武器 → `UnitView._apply_weapon()` 先全隐藏再留一个。
   其余 8 个模型**没有**武器节点，骷髅一律走 `BoneAttachment3D` 挂 `hand.r`。
3. **美术尺寸不均匀**：地板 2×2 m、墙 4×4×1 m、半墙 2×4×1 m、角柱 2.5×4×2.5 m。
   `build_arena.gd` 的步长常量就是按这些实测值定的（先按 1 m 铺过，结果一片重叠）。

### 4.2 工程里踩到的三个 Godot/工具坑（都是「静默失败」型）

| 坑 | 症状 | 判据 |
|---|---|---|
| `PackedScene.pack()` 只打包 `owner` 指向根的节点 | 脚本打印「已生成」而 `board.tscn` 只有 **76 字节** | 生成后必须打印节点数并检查文件大小 |
| glTF 实例化根节点是 `Node3D`，`as MeshInstance3D` 得 null | 计数全 0，生成空场景 | 计数必须来自「真的 add 成功」 |
| `String(x)` 在 x 已是 String 时报 `Invalid call 'String' constructor` | 整份测试文件被 GUT 判为「不继承 GutTest」而全跳过 | 测试里一律用 `str()` |

另有一个引擎层事实：**UI 工程退出时必然报 RID 泄漏**（TextServer 的 shaped-text、Font、
导入纹理），业务层零报错。已把这两类模式补进 `tools/verify.mjs` 的 `ignoreTeardown`
白名单（**本轮唯一一处共享文件改动，纯追加**），详见 §8。

## 8. 共享文件改动（一处，需知会）

`tools/verify.mjs` 的 `teardownRe` 补了两个模式：
`RID allocations of type ... were leaked at exit` 与 `RIDs of type ... were leaked`。

- **动机**：UI 工程（Label/Button + 导入纹理）退出时必然报这两类 RID 泄漏，
  业务层零报错，但原白名单只列了 `ObjectDB instances were leaked` 与
  `resources still in use at exit` 两种，于是 09 的 `load` 与 `smoke` 两步会误判失败。
- **性质**：纯追加、只放宽「加载即退出」步骤的收尾噪音，**业务层 ERROR/WARNING 仍必须为 0**，
  计数照常打印（表格里显示「收尾噪音 N 条，显式排除」）。
- 另有降噪手段：headless 下不加载 TTF（`DisplayServer.get_name() != "headless"`），
  字体是 RID 泄漏的主要来源。

`docs/00-形态路线图.md` 的进度表也补了 09 一行。若与并行的 07/11 工程冲突，保留本地版本即可。

这一轮顺带修掉两个真 bug（都是新加的伤亡断言抓出来的）：

- **结束那一 tick 的事件没被消费**：`sim.step()` 在「这一 tick 打死最后一个敌人」时返回 false，
  原代码直接 `break`，导致最后一个击杀既不计数也不播死亡标记。改成先 `_drain_events()` 再 `break`。
- **召唤物让战绩算反**：`raise_dead` 产出的召唤物 `"is_ally"` 为 true 而 `"side"` 才是它效忠的一方，
  用 `is_ally` 记账会把「敌方召唤物被我方杀掉」算成我方战功。改用 `side` 记账。
- 附带：`cleanup()` 里死亡标记用 `free()` 而不是 `queue_free()`（后者要等帧末，
  实测残留 60 个节点，下一场战斗会越叠越糊）。

新增的冒烟断言锁住这套可读性契约：战况计数 **必须与 sim 的死亡事件逐个对账**
（不能用「存活+击杀=参战数」这种伪恒等式——召唤物会让人数中途变化，写错过一次）。

## 10. 从 06 抄来的实现规范（代码不带，规范带）

1. `InputMap.add_action()` 不落盘 → 必须 `ProjectSettings.set_setting("input/...")` 再 `save()`，
   且**验证要 grep project.godot**；自检要查 `ProjectSettings`，**查 `InputMap` 是假警报**。
2. `:=` 从 Variant 推断会编译失败（`floor()` 返回 Variant、`dict["k"]` 同理）→ 一律显式标注。
3. `create_timer()` 属于 SceneTree，`create_tween()` 才是 Node 的方法。
4. 任何 `-s res://tools/*.gd` 脚本**最后必须 `quit(code)`**；运行期报错就走不到 quit，
   进程会一直挂着（本次被咬了三次）。
5. 退出噪音要**按步骤显式排除**并留痕，不能全局静默；实例化几百个 GLB 的脚本要先 `free()` 再退出。
6. 协程/函数里 `load()` 的 PackedScene 会活到函数结束 → 载入挪进独立函数返回实例。
7. 手写 `InputEventKey` 会出现 `device: 16` → 显式写 `-1`。
8. 方法名不与引擎内建方法撞名（`CameraRig.rotate()` 与 `Node3D.rotate()` 撞了，编译直接被拒）。
9. 资产实测不靠目测：glTF 的 `animations` / 包围盒 / 节点结构用脚本解析；
   **尺寸假设（1 m 网格）会直接导致关卡铺错**，实测值写在 `build_arena.gd` 的常量注释里。
10. 确定性只在 `sim/` 里成立：09 的战斗是自写定长 tick 数值模拟，不用 Godot 物理——
    这让整局跑分可以精确断言（`MatchSim.play(同一 seed)` 逐 tick 一致）。
